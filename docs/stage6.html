Stage 6 · Session 3 · after dinner · short

Swap the data, not the code

Build a 200-row database from its .sql source, point the same server at it, and change nothing else.

python3 server.py --db ../../data/all_students.db

Concept

Your server has answered about four people. Now it will answer about two hundred, and you will not change a line. The server never knew which file it was reading. It knew the shape of the table — three text columns with three fixed names — and that is all the SQL in it depends on. Point it at a bigger file with the same shape and every route keeps working, the counts just get bigger.

The bigger file does not exist yet. What exists is all_students.sql: two hundred INSERT statements under the same CREATE TABLE, in a text file. A .sql file is a script — the database's equivalent of a .c source file. Running it through sqlite3 builds the .db the way compiling builds the binary. The source is small, readable, and goes in git; the built file is what programs open, and it can always be rebuilt.

That is also why team_details.db is not in the repository and yours was built by hand in Stage 1: .db files are outputs. The header of all_students.sql lists the exact counts per college and per city, so you can check the server's answers against the source.

The switch happens on the command line. --db is read by the same sys.argv loop from Stage 0 block 5, and the path it gives replaces the default. Restart with a different --db and the same code serves different data.

Takeaway

Code depends on the shape of the data, not the data itself. Zero lines changed.

Stuck?

Nothing to write in this stage, so there is no solution folder. If all_students.db came out with 0 rows, delete it and run the build line again — a typo in the redirect creates an empty file.

Quiz

How many lines of server.py changed between Stage 5 and Stage 6?

The path came in through --db on the command line. The code depends on the table's shape, not on which file holds it.

What is all_students.sql?

Source, not output. sqlite3 all_students.db < all_students.sql runs every statement and produces the .db file.

You started the server with --db ../../data/all_students.db but /colleges still shows two names. Most likely cause?

If the old process still holds port 8080, the new one fails to start with 'Address already in use' and the old one keeps answering. Ctrl+C the old one first.

Which query can you predict from the file header without running it?

The header says Sri Prakash appears only in Kakinada with 4 rows. Names and byte counts you have to run for.
