Stage 3 · observe only

What a server actually is

A server is a program that waits. Nothing to write today: start one, poke it with curl, and read both terminals at once.

python3 demo_server.py · curl localhost:8080/hai

Concept

A server is a program that waits. It starts, it prints one line, and then it does nothing until somebody asks it something. In C you have written programs that run top to bottom and exit. This one runs a loop you never see: wait for a request, answer it, wait again. Ctrl+C is the only way it ends.

The one asking is the client. Today that is curl, a small program that builds a request, sends it, and prints whatever comes back. A request has a method (GET to ask for something, POST to send something), a path (/hai), maybe a query string (everything after the ?), and maybe a body. The server answers with a status code — 200 means fine, 400 means your request was wrong, 404 means no such path — and some content: text, or JSON.

Nothing is written in this stage. The point is to see both sides at once. Terminal 1 is the server's view: one log line per request, with the method, the path, the status and the size of the answer. Terminal 2 is the client's view: what curl got back. Same event, two windows. Every stage after this one is you standing in one of those two windows.

There are exactly three places data can travel into a server: in the path, after the ?, or in the body. The four routes of demo_server.py use one door each. The route decides which door it reads from; the client has to use that door. Step through one request below.

terminal 2 — curl
$ curl "localhost:8080/greet?name=Ravi&lang=en"{"greeting": "Hello Ravi", "lang": "en"}

Task

  1. Terminal 1 — server. Go to the Stage 3 folder and start the server. It prints two things and then waits.

    terminal 1 — server
    $ cd ~/kiet-bootcamp-3/code/stage3$ python3 demo_server.pyServing on http://localhost:8080  — Ctrl+C to stopBottle v0.13.4 server starting up (using WSGIRefServer())...Listening on http://localhost:8080/Hit Ctrl-C to quit.

  2. Terminal 2 — curl. Open a second terminal. Nothing goes in, text comes out.

    terminal 2 — curl
    $ curl localhost:8080/haiNamasthey!!!

  3. The name goes in the path.

    terminal 2 — curl
    $ curl localhost:8080/hello/RaviHow are you doing Ravi

  4. The number goes in the body, as JSON. -X POST sets the method, -H says what kind of body it is, -d is the body.

    terminal 2 — curl
    $ curl -X POST localhost:8080/isprime -H "Content-Type: application/json" -d '{"number": 17}'{"number": 17, "is_prime": true}$ curl -X POST localhost:8080/isprime -H "Content-Type: application/json" -d '{"number": 18}'{"number": 18, "is_prime": false}

  5. Same route, no body at all. The server says no, with status 400 and an error that tells you what to send.

    terminal 2 — curl
    $ curl -X POST localhost:8080/isprime{"error": "send JSON like {\"number\": 17}"}

  6. name and lang go in the query string, after the ?. Quote the URL: the shell treats a bare & as its own instruction.

    terminal 2 — curl
    $ curl "localhost:8080/greet?name=Ravi&lang=te"{"greeting": "Namasthey Ravi", "lang": "te"}$ curl "localhost:8080/greet?name=Ravi&lang=en"{"greeting": "Hello Ravi", "lang": "en"}

  7. Leave lang out: the server picks te. Leave name out: 400 again.

    terminal 2 — curl
    $ curl "localhost:8080/greet?name=Ravi"{"greeting": "Namasthey Ravi", "lang": "te"}$ curl "localhost:8080/greet?lang=te"{"error": "name is required"}

  8. -i shows the headers above the content: the status line first, then Content-Type and Content-Length. Your date and Python version will differ.

    terminal 2 — curl
    $ curl -i localhost:8080/haiHTTP/1.0 200 OKDate: Mon, 21 Sep 2026 04:43:35 GMTServer: WSGIServer/0.2 CPython/3.12.3Content-Length: 12Content-Type: text/html; charset=UTF-8 Namasthey!!!

  9. A path the server does not have. Bottle answers with its own HTML error page; the first line is what matters.

    terminal 2 — curl
    $ curl -i localhost:8080/nothingHTTP/1.0 404 Not FoundDate: Mon, 21 Sep 2026 04:43:50 GMTServer: WSGIServer/0.2 CPython/3.12.3Content-Length: 741Content-Type: text/html; charset=UTF-8 …

  10. Go to Terminal 1 and press Ctrl+C. The server stops. Now ask again from Terminal 2.

    terminal 2 — curl
    $ curl localhost:8080/haicurl: (7) Failed to connect to localhost port 8080 after 0 ms: Couldn't connect to server

    No program is listening, so there is nobody to answer. Start it again in Terminal 1 with python3 demo_server.py and the same curl works.

Takeaway

Path, query string, body — three doors into the server. The terminal on the left is the server's view; the one on the right is the client's. Same event, two windows.

Quiz

Which part of curl "localhost:8080/greet?name=Ravi&lang=en" decides which function in the server runs?

The path picks the route. The query string is data the route then reads; the host and port only pick which server program gets the request.

The server log shows "POST /isprime HTTP/1.1" 400 44. What happened?

400 is an answer. The server ran, decided the request was missing something, and said so. A crash would show a traceback in Terminal 1; a bad path would be 404; no connection would give no log line at all.

You press Ctrl+C in Terminal 1 and run curl localhost:8080/hai. What do you see?

A 404 needs a server to say it. With the process gone, nothing is listening on 8080, so the connection itself fails.

Which door does -d '{"number": 17}' use?

-d puts data in the body of the request. That is why it goes with -X POST: a GET has no body.
